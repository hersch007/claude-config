**Deploy gotcha (learned the hard way 2026-07-04):** `deploy.ps1`'s install step always runs `wp plugin install <zip> --force --activate`. This **reactivates a plugin that was deliberately deactivated on that site**, even when you're just pushing a code update, not choosing to turn it on. Concretely: deploying an updated `start-performance-tickets` zip to all 3 sites silently reactivated it on SMTI (where it had been intentionally turned off) — caught via post-deploy verification and re-deactivated. **Rule: before deploying any plugin to a site, check `wp plugin list` for its current active/inactive status there, and if inactive-by-design, either skip that site (like `ai` skips fruth) or re-deactivate immediately after and verify.** **Sites with intentionally-inactive resellable cores (never `--activate` these): SMTI** (tickets/knowledge/operations/sales/ai off — custom modules replace them) **and now FRUTH** (tickets/knowledge/operations/sales off — quotes-only, all four core tables verified 0 rows on 2026-07-10; only `sqs_quotes` has data). Fruth's four were only ever "active" because the 07-05/06 parity-work deploys force-activated them as a side-effect; they hold no data and were later silently deactivated (no `recently_activated` trace → done via WP-CLI or restore, not the WP/in-app UI). Also: the script's own exit code is unreliable (a `2>&1`-wrapped PowerShell error makes even successful deploys look failed) — always re-verify via `wp plugin list`, never trust the script's printed success/fail alone.
