**Update (smti-service 1.2.11 + 1.2.12) — write-path + page-load perf.** Richard reported status-update and ticket-to-ticket both felt slow. Two causes found: (1) `sp_smti_stage_map()` did an uncached `GET /crm/v3/pipelines/tickets/{id}` on EVERY list load, detail load, AND status update — purely to translate a stage id into a label. Measured **536 ms** per call. Now cached: `static $memo` (per-request) + transient `sp_smti_stage_map_<md5(pipeline)>` (5 min TTL) → 0.02 ms. NOTE: pipeline edits (add/rename a stage) now take up to 5 min to appear; delete that transient to force-refresh. (2) A hardcoded **`sleep(1)`** sat in ALL FOUR write handlers (`sp_smti_handle_stage_update`, `_add_note`, `_assign_owner`, `_ticket_update`) — 1000 ms of dead time per write, added defensively "so HubSpot indexes the PATCH before we re-fetch." **PROVEN UNNECESSARY:** probe on a throwaway `[SLEEPTEST]` ticket (created→PATCH+immediate GET ×6→archived) returned **6/6 consistent, 0 stale**. HubSpot `GET`-by-id is read-after-write consistent; only the SEARCH index lags, and the detail page reads by ID. All four sleeps removed. Net: status update ~3.5s → ~2.0s; ticket-to-ticket detail fetch ~1.3s → ~0.77s. USEFUL DATUM: a single HubSpot API round-trip from this host costs ~500–650 ms, so call-count is the dominant lever. (Probe was blocked by the auto-classifier until Richard explicitly authorized it — SMTI's HubSpot has nothing live yet, all tickets are self-created test data, no automations to trip.)

**DEBUGGING GOTCHA:** `.sp-btn` has `transition:background .15s,color .15s`. CSS transitions are FROZEN in a background/unfocused Chrome tab, so `getComputedStyle()` right after toggling `disabled` returns the *mid-transition* (i.e. old) color and looks like a CSS bug. Inject `*{transition:none !important}` before measuring computed colors via the browser tool.
