**Chat Core** is the next module to build — a new addon `start-performance-chat` that claims the existing `chat-core` core slot (today that slot only shows as a locked upsell teaser everywhere). Full build spec: **`docs/Chat-Core-Build-Spec.md`** in the project.

**What it is:** a *managed, AI-powered website chat* for the platform's clients. A visitor on a client's public site talks to an assistant that answers from the client's Knowledge Core, and escalates to a Service Core ticket when stuck.

**The differentiator (Richard's core idea):** the AI's **policy + guardrails are owned by the SUPER ADMIN (vendor = Richard), not the client.** Layered system prompt composed server-side — vendor policy/guardrails *wrap* the client's business-facts content, so a client can never see or weaken the safety rules. Guardrails stored structured (enforced in code), not just prose. This is the "managed service" moat.

**Confirmed decisions (2026-07-13):**
- **Deployment shape:** every client runs its OWN SP app instance (own WP install/DB); every client's public customer-facing website is a SEPARATE site (any platform). So chat back-end + `sp_chat_*` data live in the instance; the widget embeds **cross-origin** on the external public site. Same-install auto-inject is DROPPED — it's always the `<script>` embed snippet (widget `src` points at the app-instance domain, `data-sp-chat=PUBLIC_KEY`).
- **Cross-origin implications:** endpoints must do CORS + validate `Origin`/`Referer` against a new **allowed-domains** setting (`sp_chat_allowed_domains`) — both the CORS rule AND a snippet-theft control (a leaked key can't run the bot from an unlisted domain / burn the client's AI spend). Reject unlisted origins before any AI call, alongside IP-ban + rate-limit gates.
- MVP is a **Support / FAQ bot** — grounded in Knowledge Core, hands off to a ticket. NOT an open sales bot (lead capture is Phase 2).

**Richard's explicit guardrail requirements (2026-07-13) — non-negotiable, must be first-class:** (1) abuse prevention, (2) refuse to help people trying to cause harm, (3) stay out of politics, (4) never directly denigrate competitors, (5) no swearing (bot never swears + output profanity filter; abusive visitors de-escalated then banned), (6) IP blocking when attacked/abused — auto-ban (escalating cooldown, fail2ban-style) + manual super-admin blocklist, table `sp_chat_ip_blocks`, enforced before any AI call (spec §11a). Told Richard honestly: app-level IP banning stops single abusers but not distributed attacks (IP rotation) — recommend Cloudflare/WAF as the DDoS escalation path; range/CIDR blocking deferred (needs raw IPs; we hash for privacy). Captured as named refusal categories in spec §6a with defense-in-depth enforcement (grounding + vendor system prompt + structured lists `harm_categories`/`sensitive_topics`/`competitor_names`/`refuse_topics` + input/output moderation pass + kill switch + flagged audit log). All vendor-owned, client-uneditable. Told Richard honestly: no LLM guardrail is 100% jailbreak-proof — target is hard-to-bypass + fail-safe + client-can't-weaken + kill switch, not perfection.

**Design principles:** reuse, don't rebuild — calls the existing AI addon (`sp_ai_*`) for provider/key/model, grounds in Knowledge Core (`sp_kb_articles`), escalates via a `do_action('sp_chat_escalate', …)` hook (default writes `sp_tickets`; SMTI hooks HubSpot). **Key departure from the rest of the platform:** the public chat endpoint is UN-authenticated (website visitors, no login) — everything else uses `sp_team_auth`/`sp_vendor_auth`. So it needs its own session tokens, rate limiting, and prompt-injection defense. See [[core_platform_architecture]] and [[project_ai_not_a_destination]] (AI is infrastructure other modules consume — Chat Core is a consumer).

**Still open (build-time, non-blocking):** chat-specific model override vs reuse AI addon's model (lean: reuse + optional override); escalation fallback on a site with no Service Core e.g. Fruth; per-client isolation confirm.

**ENDPOINTS BUILT + LIVE-TESTED (2026-07-13, v0.2.0, `includes/chat-endpoints.php`):** public REST namespace `sp-chat/v1` with `/start`, `/send`, `/escalate` (all `permission_callback=__return_true`, i.e. unauthenticated). Gate order per call: enabled(global+client) → valid public key (`hash_equals` vs `sp_chat_public_key`, generated on activate) → allowed Origin (`sp_chat_allowed_domains`; empty=open for testing) → not IP-banned → rate limit (sessions/day/IP, msgs/session, input length) → input moderation (`sp_chat_screen_input`: injection regex + profanity → flags feed auto-ban `sp_chat_register_flag`) → KB grounding (`sp_chat_kb_retrieve` over `sp_kb_articles` WHERE visibility=`sp_chat_kb_visibility` default 'public') → `sp_chat_compose_system_prompt` → `sp_chat_ai_complete($system,$messages)` (reuses AI addon key via `sp_ai_get_api_key`; model = `sp_chat_model` override else `sp_ai_get_model`; supports Anthropic top-level `system` + OpenAI system message) → output moderation (`sp_chat_screen_output`: blocks prompt leak). CORS via `rest_pre_serve_request` only for allowed origins. Escalation fires `do_action('sp_chat_escalate',$session,$payload)`; default handler is safe no-op (captures contact on session; real ticket creation deferred to a Service-addon hook — no sp_tickets schema guessing). Install snippet + public key + allowed-domains + greeting added to the client Website Chat panel. **LIVE-VERIFIED on sp via curl:** /start returns token+greeting; /send answers via Anthropic (grounded:false when no public KB/content); **politics question was REFUSED** (guardrail composition proven); wrong key → 403.
